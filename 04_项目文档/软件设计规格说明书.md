**软硬件运行环境：**

- **操作系统**：Windows（节点A宿主机）、Ubuntu（节点B轻量虚拟机）

## 2. 概要设计（高层）

### 2.1 体系架构设计

本系统采用 **C/S（Client/Server）+ 分层架构 + 双节点分布式** 的体系架构。系统各层职责明确、高内聚低耦合。

1. **表现层（Web 前端）**：负责用户交互与页面渲染，通过 Axios 封装发起 RESTful 请求，统一携带 JWT 鉴权 Token。
2. **业务逻辑层（后端 4 个子系统）**：独立的 SpringBoot 工程，对外暴露 REST 接口。各子系统之间通过局域网 IP 发起 HTTP 远程调用，遵循《REST接口契约》。
3. **数据访问层（MySQL）**：采用双节点物理隔离部署。各子系统仅允许访问本节点的数据库，**严格禁止跨节点直连数据库**。

### 2.2 子系统职责划分说明

系统拆分为 4 个独立的高内聚子系统：

| 子系统名称          | 部署节点/端口    | 核心职责说明                                                                            |
| -------------- | ---------- | --------------------------------------------------------------------------------- |
| **统一身份权限子系统**  | 节点A / 8081 | 负责用户注册、登录；签发与校验 JWT 令牌；实现全局权限拦截（区分学生/管理员）；全局异常处理。                                 |
| **自习室座位资源子系统** | 节点A / 8082 | 负责自习室与座位的 CRUD；维护本地“时段占用记录表”；提供携带时段参数的锁座接口，实现并发防重与释放逻辑。                           |
| **预约订单流转子系统**  | 节点B / 8083 | 负责订单全生命周期状态机流转；负责违约记录的生成；**维护全局业务配置参数（`BIZ_CONFIG` 表）**；调用座位接口进行锁座/释放；调用通知接口推送消息。 |
| **监控与消息通知子系统** | 节点B / 8084 | 负责定时任务调度（扫描超时/暂离超时/到期）；负责消息的异步推送。**注：不直连其他数据库，仅作调度与通知，业务阈值统一读取订单子系统配置，不自行判断。**    |

### 2.3 双节点部署架构设计

项目实际落地采用**双节点物理隔离部署**，节点之间依靠局域网 IP 完成 REST 接口远程调用。

- **节点 A（Windows 宿主机）**
  - **部署模块**：Web 前端、身份权限子系统 (8081)、座位资源子系统 (8082)。
  - **数据库**：`auth_db`、`room_seat_db`。
- **节点 B（Ubuntu 轻量虚拟机）**
  - **部署模块**：订单流转子系统 (8083)、监控消息通知子系统 (8084)。
  - **数据库**：`order_db`、`notify_db`。

**容错边界说明**：节点A身份权限与座位查询不依赖节点B，节点B订单/通知故障时，节点A登录鉴权、自习室/座位查询仍可对外服务。订单子系统主流程依赖座位锁座与通知推送：通知子系统（8084）故障时订单业务可执行，但预约超时、暂离超时、使用到期的自动释放与消息推送失效，恢复后由定时任务按周期补偿；节点B整体不可用时订单业务不可用，节点A身份与座位查询正常。该边界与需求5.3故障场景一致，具体测试步骤不在本设计重复。

### 2.4 全局设计约束（硬性规定）

为了保障分布式环境下的稳定性与可维护性，全体开发必须遵守以下全局约束：

1. **禁止跨子系统直连数据库**：任何子系统只能访问本节点本子系统对应的数据库；跨子系统数据交互统一使用 REST 接口获取，**实体关联均为逻辑外键，严禁建立物理外键，严禁跨库执行 JOIN 查询**。
2. **统一返回与鉴权机制**：全局统一 JSON 返回格式 `{code, message, data}` 与全局错误码表；后端接口统一添加 `@CrossOrigin` 跨域注解；用户请求透传 JWT Token，定时任务/内部调用统一使用内部服务 Token (`X-Internal-Token`)，**内部接口清单由《REST接口契约》统一定义**。
3. **配置化与防硬编码**：所有服务地址、数据库地址、端口、业务参数一律写入配置文件读取。严禁在源码或提交仓库中硬编码 `localhost` 或固定 IP。
4. **定时任务架构约束**：
   - 定时任务由通知子系统（8084）统一调度触发。
   - 具体的订单状态变更、违约记录生成由订单子系统（8083）负责执行。
   - 座位释放由座位子系统（8082）负责执行。
   - **通知子系统只负责发消息，严禁直连其他数据库**。签到时长、暂离时长等业务阈值判断统一以订单子系统的配置（`BIZ_CONFIG` 表）为准。

### 2.5 高层 E-R 图与数据模型设计

系统核心实体按节点物理隔离（分为 `auth_db`、`room_seat_db`、`order_db`、`notify_db`），实体之间仅建立逻辑外键关联。

> **重要架构说明：**
> 
> 1. 下图中跨节点/跨子系统的连线（如订单与座位占用、用户与消息）均为**逻辑外键**。
> 2. 实际数据库脚本中**严禁建立物理外键**。
> 3. 订单子系统包含 `BIZ_CONFIG` 表用于维护全局业务阈值；通知子系统包含 `SCHEDULE_TASK_LOG` 表用于记录调度防重状态。
> 4. **E-R 图字段及表结构补充说明**：
>    - `ORDER_INFO` 含 `id`（逻辑外键，与 SEAT_OCCUPANCY.order_id 同类型同值）、`seat_id`、`user_id`、`status`、`start_time`、`end_time` 及暂离开始时间字段 `temp_leave_start_time`（支撑 FR-SYS-05 暂离超时扫描）。
>    - `VIOLATION` 含 `violation_time`、`reason` 字段，对齐需求6.1违约记录字段。
>    - `SEAT_OCCUPANCY` 完整字段清单：`id`、`seat_id`、`order_id`（唯一约束，一单一座）、`start_time`、`end_time`、`release_status`（逻辑释放标记）、`release_time`、`action`（释放原因）。且 `seat_id+start_time` 建有索引。
>    - `ORDER_STATUS_LOG` 表，至少包含：`id`、`order_id`、`from_status`、`to_status`、`transition_time`、`reason`，用于记录每次订单状态迁移。
>    - `BIZ_CONFIG` 通过 `config_key`/`config_value` 结构存储具体配置项（如签到截止时长、暂离保留上限、扫描周期等），并含 `description` 字段用于维护说明。

## 3. 详细设计

### 3.1 UML 模型设计

#### 3.1.1 构件图

系统由 Web 前端及 4 个后端子系统构成。构件图清晰界定了各组件的职责边界及通信协议：

（1）**数据库访问约束**：各子系统（8081/8082/8083/8084）仅通过 `<<JDBC>>` 访问各自节点部署的独立数据库（如 `auth_db`、`room_seat_db` 等），**严禁跨库直连或物理外键**。

（2）**REST 远程调用链路**：

- **前端至后端**：Web 前端通过 `<<REST-HTTP>>` 直接调用 4 个子系统对外暴露的接口。
- **内部服务交互**：订单子系统（8083）通过 `<<REST-HTTP>>` 调用座位子系统的锁座/释放接口，并调用通知子系统进行消息推送；通知子系统（8084）定时触发时，通过 `<<REST-HTTP>>` 调用订单子系统读取配置并触发超时扫描。

#### 3.1.2 部署图

系统采用**双节点物理隔离分布式部署**，依靠局域网 IP 完成跨节点 REST 接口通信。

（1）**节点 A（Windows 宿主机，IP：10.165.59.231）**：作为核心业务节点之一，部署 Web 前端（dist 静态包）、统一身份权限子系统（8081）与自习室座位资源子系统（8082），并配套部署 MySQL 数据库 `auth_db` 与 `room_seat_db`。

（2）**节点 B（Ubuntu 轻量虚拟机，IP：192.168.56.101）**：作为独立业务节点，部署预约订单流转子系统（8083）与监控与消息通知子系统（8084），并配套部署 MySQL 数据库 `order_db` 与 `notify_db`。

（3）**网络链路**：用户浏览器通过普通 HTTP 访问节点A的前端，前端通过 `<<REST-HTTP>>` 跨节点调用 8083 与 8084；订单子系统（节点B）通过 `<<REST-HTTP>>` 跨节点调用座位子系统（节点A）。

#### 3.1.3 业务用例图

系统根据用户角色划分为**学生**和**管理员**两类参与者（Actor）。

（1）**学生角色**：涵盖用户注册（FR-STU-01）、预约座位（FR-STU-05）、签到（FR-STU-06）、暂离及返回（FR-STU-10/11）、主动离开（FR-STU-12）等 12 项核心用例，覆盖了“预约—使用—释放”的全生命周期。

（2）**管理员角色**：涵盖自习室/座位管理（FR-ADM-01/02）、订单与违约查看（FR-ADM-04/05）、以及底层权限分配（FR-ADM-06）等 6 项用例。

（3）**通用功能**：用户登录（FR-STU-02）作为通用用例，被学生与管理员共同复用。

#### 3.1.4 订单状态机图

【待补充：插入成员3最新绘制的 PlantUML 状态机图 PNG】
**核心状态迁移说明**：

- **暂离超时边界**：判定条件为 `now > 暂离开始时间 + 暂离保留上限`（严格大于）。刚好等于上限时，学生返回算正常返回。
- **主动离开优先**：在“已签到（含暂离中）”状态下，学生主动签退，一律转为“已完成”，不生成违约记录，优先于暂离超时判定。
- **取消预约守卫**：待签到 → 已取消 的迁移必须满足 `now ≤ 预约开始时间 + 签到截止时长`。若超时，接口返回 1003，订单保持待签到，由定时任务按超时释放处理。

#### 3.1.5 实体类图

系统实体类按双节点物理隔离，划分为四大模块：身份权限（auth_db）、订单流转（order_db）、座位资源（room_seat_db）与监控通知（notify_db）。核心设计特征如下：

（1）**同库内实体关联**：

- **身份模块**：`sys_user` 与 `sys_role` 通过 `sys_user_role` 实现多对多关联。
- **订单模块**：以 `order_info` 为核心，一对多关联 `violation` 和 `order_status_log`；`biz_config` 为独立配置表，不建业务关联。
- **座位模块**：`room_info` 包含 `seat_info`，`seat_info` 记录 `seat_occupancy`。
- **通知模块**：`notify_message` 一对多关联 `notify_push_log`；`notify_task_log` 为独立任务日志表。

（2）**跨节点逻辑外键**：各库之间严禁物理外键，均通过业务字段实现逻辑映射。例如 `sys_user.id` 映射至订单与消息表的 `user_id`；`order_info.id` 映射至 `seat_occupancy` 的 `order_id`（一单一座）等。

（3）**三类表公共字段隔离**：业务表（如 `order_info`）包含完整公共字段；审计日志表（如 `order_status_log`）仅追加，不设 `is_deleted`；系统配置表（如 `biz_config`）依唯一键更新，不设 `is_deleted`，保障数据严谨性。

### 3.3 接口设计规范

1. **统一返回格式**：`{code, message, data}`。
2. **错误码规范**：包含 400/401/403/500 及业务错误码（1001-1007，2001-2003）。
3. **内部调用链路**：
   - 8083 调 8082：锁座、释放、状态同步。
   - 8083 调 8084：异步消息推送（不阻塞主流程）。
   - 8084 调 8083：读取业务配置、触发批量超时扫描。

## 4. 双节点部署拓扑说明

- **节点A（宿主机 Windows）**：部署前端、身份权限子系统 8081、座位资源子系统 8082，数据库 `auth_db`、`room_seat_db`。
- **节点B（Ubuntu 虚拟机）**：部署订单流转子系统 8083、监控消息通知子系统 8084，数据库 `order_db`、`notify_db`。
- **网络**：节点之间依靠局域网 IP 完成 REST 接口远程调用。

**设计局限与后续优化方向**：
目前采用网关缺位的纯 HTTP 直连调用，未引入服务注册与发现（如 Eureka/Nacos）或消息队列（如 RabbitMQ）。后续若并发量增加，消息推送可解耦为 MQ，跨节点调用可引入熔断降级机制（如 Sentinel）。
