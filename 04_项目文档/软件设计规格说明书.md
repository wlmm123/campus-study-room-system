## 2. 概要设计（高层）

### 2.1 体系架构设计

本系统采用 **C/S（Client/Server）+ 分层架构 + 双节点分布式** 的体系架构。系统各层职责明确、高内聚低耦合。

1. **表现层（Web 前端）**：负责用户交互与页面渲染，通过 Axios 封装发起 RESTful 请求，统一携带 JWT 鉴权 Token。
2. **业务逻辑层（后端 4 个子系统）**：独立的 SpringBoot 工程，对外暴露 REST 接口。各子系统之间通过局域网 IP 发起 HTTP 远程调用，遵循《REST接口契约》。
3. **数据访问层（MySQL）**：采用双节点物理隔离部署。各子系统仅允许访问本节点的数据库，**严格禁止跨节点直连数据库**。

### 2.2 子系统职责划分说明

系统拆分为 4 个独立的高内聚子系统：

| 子系统名称          | 部署节点/端口    | 核心职责说明                                                                                         |
| -------------- | ---------- | ---------------------------------------------------------------------------------------------- |
| **统一身份权限子系统**  | 节点A / 8081 | 负责用户注册、登录；签发与校验 JWT 令牌；实现全局权限拦截（区分学生/管理员）；全局异常处理。权限由 role_code（STUDENT/ADMIN）在拦截器统一校验，不单独建权限表。 |
| **自习室座位资源子系统** | 节点A / 8082 | 负责自习室与座位的 CRUD；维护本地“时段占用记录表”；提供携带时段参数的锁座接口，实现并发防重与释放逻辑。                                        |
| **预约订单流转子系统**  | 节点B / 8083 | 负责订单全生命周期状态机流转；负责违约记录的生成；**维护全局业务配置参数（`BIZ_CONFIG` 表）**；调用座位接口进行锁座/释放；调用通知接口推送消息。              |
| **监控与消息通知子系统** | 节点B / 8084 | 负责定时任务调度（扫描超时/暂离超时/到期）；负责消息的异步推送。**注：不直连其他数据库，仅作调度与通知，业务阈值统一读取订单子系统配置，不自行判断。**                 |

### 2.3 双节点部署架构设计

项目实际落地采用**双节点物理隔离部署**，节点之间依靠局域网 IP 完成 REST 接口远程调用。

- **节点 A（Windows 宿主机）**
  - **部署模块**：Web 前端、身份权限子系统 (8081)、座位资源子系统 (8082)。
  - **数据库**：`auth_db`、`room_seat_db`。
- **节点 B（Ubuntu 轻量虚拟机）**
  - **部署模块**：订单流转子系统 (8083)、监控消息通知子系统 (8084)。
  - **数据库**：`order_db`、`notify_db`。

**容错边界说明**：节点A身份权限与座位查询不依赖节点B，节点B订单/通知故障时，节点A登录鉴权、自习室/座位查询仍可对外服务。订单子系统主流程依赖座位锁座与通知推送：通知子系统（8084）故障时订单业务可执行，但预约超时、暂离超时、使用到期的自动释放与消息推送失效，恢复后由定时任务按周期扫描尚未终态的订单并推进至终态（故障期间未送达的消息不做补推，恢复后新事件推送恢复正常）；**故障期间未被处理的订单，其 `seat_occupancy` 未释放记录仍占着该时段，其他学生预约该时段返回 `1001`（锁住而非超卖），恢复释放后自动可约**；节点B整体不可用时订单业务不可用，节点A身份与座位查询正常。该边界与需求5.3故障场景一致，具体测试步骤不在本设计重复。

### 2.4 全局设计约束（硬性规定）

为了保障分布式环境下的稳定性与可维护性，全体开发必须遵守以下全局约束：

1. **禁止跨子系统直连数据库**：任何子系统只能访问本节点本子系统对应的数据库；跨子系统数据交互统一使用 REST 接口获取，**实体关联均为逻辑外键，严禁建立物理外键，严禁跨库执行 JOIN 查询**。
2. **统一字符集与排序规则**：四个数据库统一使用 `utf8mb4` + `utf8mb4_general_ci`，禁止各库使用不同排序规则，避免逻辑外键比较时出现 `Illegal mix of collations`。
3. **统一返回与鉴权机制**：全局统一 JSON 返回格式 `{code, message, data}` 与全局错误码表；后端接口统一添加 `@CrossOrigin` 跨域注解；用户请求透传 JWT Token，定时任务/内部调用统一使用内部服务 Token (`X-Internal-Token`)，**内部接口清单由《REST接口契约》统一定义**。
4. **配置化与防硬编码**：所有服务地址、数据库地址、端口、业务参数一律写入配置文件读取。严禁在源码或提交仓库中硬编码 `localhost` 或固定 IP。
5. **定时任务架构约束**：
   - 定时任务由通知子系统（8084）统一调度触发。
   - 具体的订单状态变更、违约记录生成由订单子系统（8083）负责执行。
   - 座位释放由座位子系统（8082）负责执行。
   - **通知子系统只负责发消息，严禁直连其他数据库**。签到时长、暂离时长等业务阈值判断统一以订单子系统的配置（`BIZ_CONFIG` 表）为准。

### 2.5 高层 E-R 图与数据模型设计

系统核心实体按节点物理隔离（分为 `auth_db`、`room_seat_db`、`order_db`、`notify_db`），实体之间仅建立逻辑外键关联。

> **重要架构说明：**
> 
> 1. 下图中跨节点/跨子系统的连线（如订单与座位占用、用户与消息）均为**逻辑外键**。
> 2. 实际数据库脚本中**严禁建立物理外键**。
> 3. 订单子系统包含 `biz_config` 表用于维护全局业务阈值；通知子系统包含 `notify_task_log` 表用于记录调度执行状态，`notify_push_log` 记录消息推送日志。`biz_config` 为独立配置表，不与 `order_info` 建立业务关联，ER 图不画关系线。
> 4. **E-R 图字段及表结构补充说明**：
>    - `VIOLATION` 含 `violation_time`、`reason` 字段，对齐需求6.1违约记录字段。
>    - `SEAT_OCCUPANCY` 完整字段清单：`id`、`seat_id`、`order_id`（唯一约束，一单一座）、`start_time`、`end_time`、`release_status`（逻辑释放标记）、`checkin_flag`（**该订单的人是否已到达：0 未到、1 已到**，由 3.5 在签到/暂离/返回时置 1，置 1 后不回落）、`release_time`、`action`（释放原因）。且 `seat_id+start_time` 建有索引。**`checkin_flag` 是座位侧判断"覆盖此刻的那单人到了没"的唯一本库依据**——座位侧不能跨库查订单状态，也不能反向调用订单接口。
>    - `ORDER_INFO` 含 `id`（逻辑外键，与 `SEAT_OCCUPANCY.order_id` 同类型同值）、`seat_id`、`user_id`、`status`、`start_time`、`end_time`、暂离开始时间字段 `temp_leave_start_time`（支撑 FR-SYS-05 暂离超时扫描）及进入终态时间 `finish_time`（仅终态有值，进行中为NULL）。
>    - `BIZ_CONFIG` 通过 `config_key`/`config_value` 结构存储具体配置项（签到截止时长、暂离保留上限、档位单位、可选档位、最大档位），并含 `description` 字段用于维护说明；**服务启动时加载，改配置需重启生效**。表中 `scan_interval_seconds` 仅为留档，实际调度周期取自通知子系统 8084 自身配置文件（见《REST接口契约》4.3）。
>    - `seat_info` 状态更新规则：**座位状态只有四个写入者**——①锁座（**仅当所锁时段覆盖当前时刻且座位原为“可用”→ `已预约`**，其余情况不动）、②定时任务“预约生效”（待签到订单进入时段且座位原为“可用”→ `已预约`）、③签到/暂离/返回（`已占用`/`暂离中`）、④释放回落（3.4）。**`已占用`/`暂离中` 只能由 ③ 写入**。
>    - seat_info 释放状态回落规则（完整判定见 3.2.2「释放状态更新规则」，此处只列结论）：释放该订单的时段占用记录后，**只按当前时刻判定、不问未来有无预约**——① 维护/停用 → 保持；② 仍存在覆盖当前时刻（`start_time ≤ 当前时间 < end_time`）的其他未释放记录 → **看该记录的 `checkin_flag`**：为 1（那人已到）则保持 `已占用`/`暂离中` 不变，为 0（那人还没到）则置 `已预约`；③ 不存在覆盖当前时刻的记录 → 回“可用”（**不论未来是否还有未释放记录**）。即释放的落点既不是固定“可用”，也不受“未来有没有预约”影响——未来预约只影响该时段查询的 `bookable`，不影响此刻状态。

## 3. 详细设计

### 3.1 UML 模型设计

#### 3.1.1 构件图

系统由 Web 前端及 4 个后端子系统构成。构件图清晰界定了各组件的职责边界及通信协议：

（1）**数据库访问约束**：各子系统（8081/8082/8083/8084）仅通过 `<<JDBC>>` 访问各自节点部署的独立数据库（如 `auth_db`、`room_seat_db` 等），**严禁跨库直连或物理外键**。

（2）**REST 远程调用链路**：

- **前端至后端**：Web 前端通过 `<<REST-HTTP>>` 直接调用 4 个子系统对外暴露的接口。
- **内部服务交互：订单子系统（8083）通过 `<<REST-HTTP>>` 调用座位子系统的锁座/释放接口，并调用通知子系统进行消息推送；通知子系统（8084）定时触发时，通过 `<<REST-HTTP>>` 触发订单子系统执行超时扫描**（业务阈值由订单子系统内部自行读取判断）。

#### 3.1.2 部署图

系统采用**双节点物理隔离分布式部署**，依靠局域网 IP 完成跨节点 REST 接口通信。

（1）**节点 A（Windows 宿主机，IP：10.165.59.231）**：作为核心业务节点之一，部署 Web 前端（dist 静态包）、统一身份权限子系统（8081）与自习室座位资源子系统（8082），并配套部署 MySQL 数据库 `auth_db` 与 `room_seat_db`。

（2）**节点 B（Ubuntu 轻量虚拟机，IP：192.168.56.101）**：作为独立业务节点，部署预约订单流转子系统（8083）与监控与消息通知子系统（8084），并配套部署 MySQL 数据库 `order_db` 与 `notify_db`。

（3）**网络链路**：用户浏览器通过普通 HTTP 访问节点A的前端，前端通过 `<<REST-HTTP>>` 跨节点调用 8083 与 8084；订单子系统（节点B）通过 `<<REST-HTTP>>` 跨节点调用座位子系统（节点A）。

#### 3.1.3 业务用例图

系统根据用户角色划分为**学生**和**管理员**两类参与者（Actor）。

（1）**学生角色**：涵盖用户注册（FR-STU-01）、预约座位（FR-STU-05）、签到（FR-STU-06）、暂离及返回（FR-STU-10/11）、主动离开（FR-STU-12）等 12 项核心用例，覆盖了“预约—使用—释放”的全生命周期。

（2）**管理员角色**：涵盖自习室/座位管理（FR-ADM-01/02）、订单与违约查看（FR-ADM-04/05）、以及底层权限分配（FR-ADM-06）等 6 项用例。

（3）**通用功能**：用户登录（FR-STU-02）作为通用用例，被学生与管理员共同复用。

#### 3.1.4 订单状态机图

**核心状态迁移说明**：

- **取消预约守卫**：待签到 → 已取消 的迁移必须满足 `now ≤ 预约开始时间 + 签到截止时长`。若超时，接口返回 1003，订单保持待签到，由定时任务按超时释放处理。
- **暂离超时边界**：判定条件为 `now > 暂离开始时间 + 暂离保留上限`（严格大于）。刚好等于上限时，学生返回算正常返回。
- **主动离开优先**：在“已签到（含暂离中）”状态下，学生主动签退，一律转为“已完成”，不生成违约记录，优先于暂离超时判定。
- **使用到期优先原则**：当“暂离超时”与“到达使用截止时间”同时满足时，一律走“已完成”分支，不记暂离超时，不生成违约记录。
- **终态幂等**：已取消、已完成、暂离超时释放、超时释放全部为终态；定时任务扫描直接跳过，不再发生任何状态迁移。
- **推送口径**：学生主动返回触发的到期分支（契约 4.2.5①）不推送消息；仅定时任务到期分支（契约 4.2.12①）推送 `USE_EXPIRED_COMPLETE`，推送失败仅记日志，不阻塞主流程。

#### 3.1.5 实体类图

系统实体类按双节点物理隔离，划分为四大模块：身份权限（auth_db）、订单流转（order_db）、座位资源（room_seat_db）与监控通知（notify_db）。核心设计特征如下：

（1）**同库内实体关联**：

- **身份模块**：`sys_user` 与 `sys_role` 通过 `sys_user_role` 实现多对多关联。
- **订单模块**：以 `order_info` 为核心，一对多关联 `violation` 和 `order_status_log`；`biz_config` 为独立配置表，不建业务关联。
- **座位模块**：`room_info` 包含 `seat_info`，`seat_info` 记录 `seat_occupancy`。
- **通知模块**：`notify_message` 一对多关联 `notify_push_log`；`notify_task_log` 为独立任务日志表。

（2）**跨节点逻辑外键**：各库之间严禁物理外键，均通过业务字段实现逻辑映射。例如 `sys_user.id` 映射至订单与消息表的 `user_id`；`order_info.id` 映射至 `seat_occupancy` 的 `order_id`（一单一座）等。

（3）**三类表公共字段隔离**：业务表（如 `order_info`）包含完整公共字段；审计日志表（如 `order_status_log`）仅追加，不设 `is_deleted`；系统配置表（如 `biz_config`）依唯一键更新，不设 `is_deleted`，保障数据严谨性。

#### 3.1.6 预约座位顺序图

**核心时序说明**：

**防超卖机制**：订单系统生成全局唯一 `orderId`（若为雪花 ID，序列化返回前端时必须转为 String 防精度丢失），先调用座位子系统锁座，锁座成功后才落库生成订单。**锁座成功只新增一条 `seat_occupancy` 记录**；仅当所锁时段覆盖当前时刻且座位原为“可用”时才顺带置 `已预约`（顺序图中的座位状态更新须带上该条件，不得无条件出现"座位转已预约"）。

**异常处理与补偿**：若锁座失败（返回 1001/1003/1006 等），则不生成订单。若锁座成功但本地订单落库失败，则反向调用座位释放接口进行补偿，并返回 HTTP 500。

**消息异步推送**：订单落库成功后，异步调用通知子系统进行消息推送，推送失败仅记录日志，不阻塞主流程。

### 3.2 数据库表结构设计

**(全局规范：除 `order_info.id` 按雪花/应用层预生成外，其余表主键统一 BIGINT 自增；所有库统一 `utf8mb4` + `utf8mb4_general_ci`；各子系统独立建库，无物理外键)**

#### 3.2.1 身份权限子系统（auth_db）

**(1) `sys_user`（用户信息表）**

| username    | VARCHAR(50)  | NOT NULL, 唯一         | 登录账号（学号），全局唯一 |
| password    | VARCHAR(100) | NOT NULL             | 加密密码          |
| real_name   | VARCHAR(50)  |                      | 真实姓名          |
| status      | TINYINT      | 默认 1                 | 账号状态：1正常，0禁用  |
| create_time | DATETIME     | 默认 CURRENT_TIMESTAMP | 创建时间          |
| update_time | DATETIME     | 默认 CURRENT_TIMESTAMP | 更新时间          |
| is_deleted  | TINYINT(1)   | 默认 0                 | 逻辑删除：0未删，1已删  |

**(2) `sys_role`（角色信息表）**

| 字段名         | 类型          | 约束/索引                | 说明                     |

**时段冲突校验与并发控制**：  
（1）冲突校验条件：`seat_id=? AND is_deleted=0 AND release_status=0 AND start_time < ? AND end_time > ?`；无冲突才插入占用记录，冲突返回 `1001`；  
（2）并发控制：锁座事务内先 `SELECT id FROM seat_info WHERE id=? FOR UPDATE` 锁定座位行，再执行冲突校验与插入，保证同一座位并发锁座串行化；不得仅靠普通索引，避免并发插入重复占用。

(3)锁座入参必须包含由订单侧计算好的 `startTime` 和 `endTime`，座位侧直接以此做区间重叠判断，不自行换算时长。

**锁座状态更新规则**：  
锁座成功并插入占用记录后：**仅当所锁时段覆盖当前时刻（`startTime ≤ 当前时间 < endTime`，即约的是立即开始的时段）且该座位当前为 `可用` 时，置为 `已预约`**；其余情况（约未来时段、座位当前为 `已占用`/`暂离中`）**一律不改动状态**。理由：`已预约` 只表达"此刻被订住、人还没签到"；若对"未来时段被订住"也写，会出现"A-01 晚上 19:00 有人约、下午空着却显示已预约"的误导。`维护/停用` 已在冲突校验前直接拦截返回 `1006`；`已占用`/`暂离中` 只能由 3.5 写入。

**释放状态更新规则**：释放该 `orderId` 对应的占用记录后，座位粗状态**只按当前时刻判定，不问未来有没有预约**：
① 若处于 `维护`/`停用` → **保持原状态**（优先于其余各档）；
② 若该座位仍存在**覆盖当前时刻**（`start_time ≤ 当前时间 < end_time`）的其他未释放占用记录 → **看该记录（覆盖记录）的 `checkin_flag`**：
　- `checkin_flag = 1`（那单的人已经到过）→ **保持座位当前状态不变**（`已占用` 或 `暂离中`，由 3.5 早前写入），**本接口不得把它覆盖成 `已预约`**；
　- `checkin_flag = 0`（那单的人还没到）→ 置 **`已预约`**。
　两种情况都回传 `coveringOrderId` 供调用方核对。`已占用`/`暂离中` 只能由 3.5 写入，释放回落不得越权覆盖"人已到"这一事实；而座位侧判断"人到了没"的唯一本库依据就是 `checkin_flag`（座位库不能跨库查订单状态，也不能反向调用订单接口）；
③ 若不存在覆盖当前时刻的未释放记录 → 回 **"可用"**，**无论未来是否还有开始时间晚于当前时刻的未释放记录**。

> **释放即腾空**：记录置 `release_status=1` 后，其 `[start_time, end_time)` 立即不再参与冲突判断，紧随其后的空档（无其他未释放记录时）立即 `bookable=true`、可被锁座。`seat_info.status` 只是展示快照，**锁定逻辑一律以 `seat_occupancy` 为准**，不得用 `status` 判断能否预约。典型：A 单 8:00-9:00 到期、B 单 9:00-10:00 同座位，9:00 释放 A 时——B 尚未签到则状态为"**已预约**"（`checkin_flag=0`），B 已签到则**保持"已占用"**（`checkin_flag=1`）；两种情况 A 的时段都已腾空，10:00 之后立即恢复可约。

> 旧规则"无覆盖当前时刻但有未来预约 → 置已预约"已在 V3.4 废弃：它会让"晚上有约、下午空着"的座位整个下午显示为已预约，而实际下午可约。`status` 是此刻快照，不承载未来预约；未来时段可约性见下方 `bookable` 规则。

**时段可约性查询规则（契约 3.2 的 `bookable`）**：给定 `[startTime, endTime)`，若该座位非维护/停用，且该时段内不存在未释放占用记录（`release_status=0` 且 `start_time < endTime AND end_time > startTime`），则 `bookable=true`，否则为 `false`。判定口径与锁座（契约 3.3(2)）**必须完全一致**，避免出现"列表显示可约、锁座返回 1001"。本查询只读、不加锁，结果仅为查询时刻的参考值。

**设置维护/停用规则（契约 3.6.7）**：管理员设置维护/停用时，唯一门槛是**该座位已无任何未释放的时段占用记录**——存在覆盖当前时刻的记录（正在使用/暂离中）→ 拒绝 `1006` 并提示"座位正在使用中"，清单为空；仍存在未来预约 → 拒绝 `1006` 并附 `affectedOrders` 清单；两者都没有 → 设置成功，清单为空。`forced`／`force` 之类的"强制"开关**已取消**（V3.4）：绕过检查会留下"座位=维护、订单=待签到"的死数据。座位侧**不取消订单**（调用链为订单→座位的单向下行），须由调用方先取消受影响订单、再重新提交设置。

- **网络**：节点之间依靠局域网 IP 完成 REST 接口远程调用。

**设计局限与后续优化方向**：
目前采用网关缺位的纯 HTTP 直连调用，未引入服务注册与发现（如 Eureka/Nacos）或消息队列（如 RabbitMQ）。后续若并发量增加，消息推送可解耦为 MQ，跨节点调用可引入熔断降级机制（如 Sentinel）。
