## 1. 引言

### 1.1 项目背景

高校自习室座位资源紧张，学生找座、占座、违约占座现象普遍，管理方缺乏有效的座位状态与预约行为管理手段。本项目开发一套校园自习室分布式预约管理系统，支持学生在线查询自习室与座位、按时间段预约、签到、暂离、离开、取消，支持管理员维护自习室与座位、查看预约与违约情况，并通过消息通知实现预约超时提醒、暂离超时提醒与座位自动释放。

### 1.2 开发目标

- 实现自习室、座位资源的统一管理与实时状态展示；
- 实现"预约—签到—暂离/返回—离开/到期"完整订单流转与状态机管理；
- 实现预约超时未签到自动释放、暂离超时自动释放，并推送消息、生成违约记录；实现使用到期自动释放座位；
- 采用双节点分布式部署，验证"部分子系统宕机，其余业务可继续运行"的容错能力；
- 按软件工程规范完成需求、设计、开发、测试、部署全流程文档与交付物。

### 1.3 项目范围

**包含**：Web前端；统一身份权限子系统、自习室座位资源子系统、预约订单流转子系统、监控与消息通知子系统共4个后端子系统；双节点部署；三套数据库脚本；全套UML模型；项目文档与演示材料。

**不包含**：移动端App、第三方支付、校园统一身份认证对接、真实短信/邮件通道（消息通知以系统内消息/模拟推送实现）。

### 1.4 预期用户

- **学生用户**：查询自习室与座位、按时间段预约、签到、暂离、返回、离开/签退、取消预约、查看订单与消息。
- **管理员**：维护自习室与座位、管理座位状态、查看预约订单与违约记录、管理用户（依权限）。
- **系统（定时任务）**：扫描超时未签到、暂离超时、使用到期的预约，释放座位并推送消息。

### 1.5 开发约束

- 架构：C/S + 分层，双节点物理隔离分布式部署；
- 节点A（Windows宿主机）：前端、身份权限子系统（8081）、座位资源子系统（8082），数据库 auth_db、room_seat_db；
- 节点B（Ubuntu虚拟机）：订单流转子系统（8083）、监控消息通知子系统（8084），数据库 order_db、notify_db；
- 节点间通过局域网IP进行REST远程调用；
- 硬性约束：禁止跨子系统直连数据库；后端接口统一 `@CrossOrigin`；禁止硬编码localhost，IP配置化；
- 技术栈：SpringBoot + MySQL + 前端框架（按小组选型），JUnit单元测试。

## 2. 总体描述

### 2.1 用户角色分析

| 角色       | 说明         | 主要权限                                          |
| -------- | ---------- | --------------------------------------------- |
| 学生       | 已注册登录的在校学生 | 查询自习室/座位、按时间段预约、签到、暂离、返回、离开/签退、取消预约、查看本人订单与消息 |
| 管理员      | 系统管理用户     | 自习室/座位增删改查、座位状态管理、订单与违约查看、用户与权限管理             |
| 定时任务（系统） | 后台调度角色     | 扫描超时未签到/暂离超时/使用到期订单、释放座位、触发消息推送               |

### 2.2 整体业务场景

1. 学生注册/登录，获取JWT令牌；
2. 学生浏览自习室列表与座位状态，选择可用座位并选择使用时间段（开始时间+时长档位），发起预约：先调用座位资源子系统锁座接口（入参含时段），锁座成功后才生成订单（待签到），座位转"已预约"；锁座失败不生成订单；
3. 签到截止时间前，学生可主动取消预约，座位释放；
4. 学生在签到窗口内（预约开始时间至预约开始时间+签到截止时长）签到，订单转已签到，座位转"已占用"，进入使用期；**预约开始前不可签到**；
5. 使用期内学生可"暂离"（座位转"暂离中"，仍锁定）；暂离后返回需重新签到恢复"已占用"；返回时系统实时校验：已到使用截止时间按到期优先处理（不违约），已暂离超2小时且未到期按暂离超时释放（违约），否则正常返回；暂离超过2小时未返回且未到使用截止时间、学生也未主动操作，定时任务自动转"暂离超时释放"，座位释放并生成违约记录、推送消息；暂离中已到使用截止时间的，按使用到期优先转"已完成"、不违约；
6. 使用期内学生可主动"离开/签退"，订单转"已完成"，座位释放；
7. 到使用截止时间仍未主动离开，定时任务自动转"已完成"并释放座位；
8. 未在签到截止时间前签到：定时任务将订单转"超时释放"，座位释放，生成违约记录并推送消息；
9. 管理员维护自习室与座位、调整座位状态、查看订单与违约情况；
10. 全流程跨节点通过REST调用；通知子系统故障时各类自动释放与消息推送失效，恢复后由定时任务按周期扫描补偿。

## 3. 外部接口需求

### 3.1 登录鉴权

- 采用JWT：登录成功后签发Token，前端后续请求统一在请求头携带 `Authorization: Bearer <token>`；
- 后端对受保护接口校验Token有效性、过期与角色权限，非法/过期Token统一返回标准错误码；
- 跨节点调用同样遵循Token鉴权与统一返回格式；用户发起的跨节点调用透传用户Token。

### 3.2 前端交互约束

- 前端通过统一axios封装发起请求，BaseURL配置化，禁止硬编码IP；
- 统一解析后端JSON返回与全局错误提示；
- 表单需前端校验（必填、格式、长度、时段合法性），后端二次校验；
- 页面覆盖：登录、自习室座位、预约下单（选时段）、订单管理（含暂离/返回/离开）、消息提醒、管理员管理。

### 3.3 跨节点REST调用约束

- 节点A与节点B之间通过局域网IP进行REST远程调用，调用方IP、端口一律从配置文件读取，禁止硬编码；
- 跨节点接口遵循统一Token鉴权与全局JSON返回格式、全局错误码；
- 禁止跨节点直连对方数据库，跨子系统数据一律通过REST接口获取；
- 节点间调用失败须返回明确错误信息，不得导致调用方服务崩溃；
- 系统定时任务无用户Token，通过内部服务鉴权机制调用内部业务接口（超时/暂离超时/到期订单查询、座位锁定/释放、消息推送等），内部接口清单与鉴权机制由《REST接口契约》统一定义；需求层仅约定"内部接口+契约定义"，不约定具体实现形式。

> **【系统定时任务架构总则】**

**预约时长说明**：档位固定1至8小时。学生选开始时间后，前端按“开始+档位≤预约开始日次日00:00:00”过滤档位；后端校验“时长∈1至8 且 开始+时长≤预约开始日次日00:00:00（等于时视为到当天结束、不跨天）”。订单的预约结束时间=开始时间+所选时长，不跨自然日。

**订单状态机（明确闭环）**：

- 待签到 →（签到，守卫：预约开始时间≤now≤预约开始时间+签到截止时长）已签到
- 待签到 →（取消）已取消
- 待签到 →（超时未签到，定时任务，条件：now>预约开始时间+签到截止时长）超时释放 + 违约记录 + 消息
- 已签到 →（暂离）已签到（座位暂离中）
- 已签到（暂离中）→（返回重新签到，守卫：now<暂离开始时间+暂离保留上限 且 now<预约结束时间）已签到（座位已占用）
- 已签到（暂离中）→（学生返回时已暂离超时且未到期：now≥暂离开始时间+暂离保留上限 且 now<预约结束时间）暂离超时释放 + 违约记录 + 消息（学生主动触发，立即闭环）
- 已签到（暂离中）→（学生返回时已到期：now≥预约结束时间）已完成 + 释放座位（不违约，使用到期优先；学生主动触发，立即闭环）
- 已签到 →（主动离开）已完成
- 已签到 →（到使用截止时间未离开，定时任务）已完成 + 释放座位
- 已签到（暂离中）→（到达使用截止时间未返回，定时任务）已完成 + 释放座位（**使用到期优先，不生成违约记录**）
- 已签到（暂离中）→（暂离超2小时未返回且未到使用截止时间，定时任务）暂离超时释放 + 违约记录 + 消息
- 已取消、超时释放、暂离超时释放、已完成为终态

> 优先级说明：当"暂离超2小时"与"到达使用截止时间"同时满足时，按**使用到期优先**处理，走"已完成 + 释放座位、不生成违约记录"分支，不记暂离超时。该优先级在定时任务路径（FR-SYS-04/05）与学生主动返回路径（FR-STU-11）上一致适用。
>
> 幂等说明：学生主动返回触发的"暂离超时释放"/"已完成"与定时任务触发的同类迁移结果一致；订单进入终态后，定时任务扫描跳过，不重复生成违约记录或消息。

## 5. 非功能性需求

### 5.1 性能

- 常规查询接口在双节点局域网环境下响应时间≤2秒；
- 座位预约需保证同一座位同一时段不被重复预约：预约前必须调用座位资源子系统锁座接口（入参含时段），以锁座成功为订单生成前提。

### 5.2 安全性

- 密码加密存储；JWT鉴权；受保护接口做角色权限拦截；
- 非法Token、越权访问统一返回标准错误码；
- 禁止跨子系统直连数据库，减少数据越权面。

### 5.3 容错性（分布式容错需求，重点）

- 系统采用双节点部署，部分子系统宕机时，其余业务可继续运行；
- **故障场景一（仅关停8084通知子系统，主验证场景）**：订单子系统8083业务可用（预约/签到/暂离/返回/离开可执行），但预约超时、暂离超时、使用到期的座位不会自动释放、消息推送失效；节点A身份权限、座位查询业务正常；恢复8084并重启后，定时任务按周期扫描补偿，座位自动释放、消息推送恢复。
- **故障场景二（节点级扩展验证场景）**：在宿主机上**断开节点B网络（禁用虚拟网卡或防火墙阻断），并停止节点B的8083、8084服务进程**，模拟节点B整体不可用；验证节点A登录鉴权、身份权限、自习室/座位查询等业务正常可继续对外服务，订单业务不可用；恢复时先确认节点B MySQL服务处于正常运行状态（本场景MySQL未被强制终止），再启动8083、8084服务，验证定时任务补偿（超时/暂离超时/到期订单补处理、消息补推）。**本场景不以强制断电作为验收操作，避免将数据库崩溃恢复能力混入业务容错结论。**
- 跨节点调用失败应有明确错误提示，不得导致调用方服务崩溃；
- 故障隔离边界：通知子系统故障时，节点A登录鉴权、身份权限、自习室/座位查询业务不受影响；订单子系统因依赖通知与座位状态回写，可能出现消息缺失或释放延迟，须在《软件测试报告》中明确记录该现象及恢复验证结果。

### 5.4 可维护性

- 分层架构、子系统边界清晰；统一返回格式与全局异常处理；
- 配置化（IP、端口、数据库连接、业务参数）便于部署迁移；
- UML模型与代码保持一致，文档随变更同步更新。

## 6. 数据需求

### 6.1 业务数据项（按子系统）

- 身份权限：用户、角色、权限、用户角色关联、角色权限关联；
- 座位资源：自习室、座位（状态枚举：可用、已预约、已占用、暂离中、维护、停用；状态仅表当前时刻粗状态，时段可约性见下方说明）；座位资源子系统本地维护**按时段的占用记录**，作为锁座与并发防重的判据；
- 订单流转：预约订单（状态：待签到、已签到、已取消、超时释放、暂离超时释放、已完成；含预约开始/结束时间、暂离开始时间）、违约记录（用户id、订单id、违约类型、违约时间、原因）；违约记录归order_db（订单子系统）；
- 消息通知：消息记录、超时/暂离超时/到期任务相关数据；消息归notify_db（通知子系统）。

**订单状态与座位状态跨节点映射（业务约束）**：

| 订单事件                | 订单状态   | 座位状态  | 说明                        |
| ------------------- | ------ | ----- | ------------------------- |
| 预约成功（锁座成功）          | 待签到    | 已预约   | 已锁定，他人不可约                 |
| 签到成功                | 已签到    | 已占用   | 人在座使用                     |
| 暂离                  | 已签到    | 暂离中   | 暂离，座位仍锁定，开始计时             |
| 暂离返回（重新签到，未超时未到期）   | 已签到    | 已占用   | 回到使用，计时清零                 |
| 暂离返回时已暂离超时且未到期      | 暂离超时释放 | 可用    | 释放+违约记录（学生主动触发）           |
| 暂离返回时已到使用截止时间       | 已完成    | 可用    | 使用到期优先，释放，**不违约**（学生主动触发） |
| 主动离开/签退             | 已完成    | 可用    | 释放                        |
| 取消                  | 已取消    | 可用    | 释放                        |
| 超时未签到释放             | 超时释放   | 可用    | 释放+违约记录                   |
| 暂离超2小时释放（且未到使用截止时间） | 暂离超时释放 | 可用    | 释放+违约记录                   |
| 暂离中到达使用截止时间         | 已完成    | 可用    | 使用到期优先，释放，**不违约**         |
| 到期自动完成              | 已完成    | 可用    | 释放，不违约                    |
| 管理员维护/停用            | —      | 维护/停用 | 不可用                       |

**【状态枚举统一】** 座位状态必须严格使用"可用、已预约、已占用、暂离中、维护、停用"这6个词，前端展示、数据库字段、接口参数必须一字不差，严禁自造同义词。

**说明：**

1. "已预约、已占用、暂离中"均为不可被他人预约的占用态，区别仅在业务语义（待签到/在座使用/暂离未归）。
2. 座位"状态"字段仅表达当前时刻粗状态，用于展示与管理；某座位某时段能否预约，由**座位资源子系统在本地按时段维护的占用记录**进行冲突校验。锁座接口须含时段入参，以**本地时段不重叠**为并发防重判据；锁座成功后，订单子系统方可生成订单。占用记录表的具体表名、字段与锁机制实现，由成员2在设计阶段定义。
3. 释放由订单事件驱动，座位资源子系统释放该订单对应的**时段占用记录**，而非整座置可用；仅当该座位**无任何未释放的时段占用记录**且非维护/停用时，座位状态才回到"可用"。
4. 具体接口形态由《REST接口契约》定义。

### 6.2 数据保存规则

- 节点A数据库：auth_db（身份权限）、room_seat_db（座位资源）；
- 节点B数据库：order_db（订单、违约记录）、notify_db（通知）；
- 各子系统仅访问本库，跨库数据通过REST获取；
- 订单状态迁移需留痕（状态、时间）；消息与业务事件关联保存；
- 三套脚本：total_init.sql（单机归档备份，双节点不执行）、init_nodeA.sql、init_nodeB.sql。

**测试环境例外与验收口径：**

1. 上述参数须支持外部配置文件动态修改。开发调试、集成测试、演示视频录制环境允许将"签到截止时长""暂离保留上限""定时扫描周期""可选时长档位"缩短至分钟级（如1~3分钟），仅用于快速验证定时任务触发与状态机闭环，**不改变任何业务规则与代码逻辑**；测试报告须注明本次测试实际使用的配置值及对应环境（测试环境缩短值/验收环境默认值）。

4. **预约时间边界**：预约开始时间须≥下单时刻（当前时间）；预约开始时间+所选时长须≤预约开始日次日00:00:00（等于时视为到当天结束、不跨天）；"当日"指预约开始时间所在自然日；不设"最多提前天数"上限，学生可预约下单时刻之后、任意自然日内（单次不跨天）的合法时段；单次预约不得跨自然日。

## 7. 验收标准

1. 需求文档章节完整、业务需求无遗漏、项目边界清晰，评审记录作为附录；
2. 双节点环境下4个子系统可正常启动，核心业务流程跑通：
   - 流程A：登录→查座→选时段预约→取消；
   - 流程B：登录→查座→选时段预约→签到→暂离→返回重新签到→主动离开释放；
   - 流程C：预约→超时未签到自动释放+违约+消息；
   - 流程D：签到→暂离超2小时自动释放+违约+消息；
   - **流程E（边界）**：预约开始前尝试签到被拒绝；暂离超时后、定时任务扫描前学生主动返回，立即按"暂离超时释放"处理并记违约；暂离中已到使用截止时间后学生主动返回，按"已完成"处理且不记违约；
   - **流程F（档位边界）**：17:00预约时8h档位不可选（17+8=次日01:00，晚于预约开始日次日00:00:00）；23:00仅可选1h（23+1=次日00:00:00，等于、合法；2h=次日01:00，非法）；16:00选8h=次日00:00:00，**等于、合法**。
3. 单元测试完成，集成测试与分布式容错专项测试通过：分别验证两个故障场景——仅关停8084：订单业务可用、超时/暂离超时/到期均不释放、消息失效；挂起节点B（断网+停进程）：订单业务不可用、节点A登录查座正常；两种场景恢复后均能自动释放、推送恢复；
4. 所有后端接口含 `@CrossOrigin` 跨域注解，且无硬编码localhost/IP（服务地址、数据库地址、端口、业务参数均配置化读取），禁止跨子系统直连数据库，校验通过。**执行方式：各后端开发人员在交付jar前逐项自查，并在交付说明中附《硬性约束自查表》（含检查项、结果、证据说明）；成员6在最终交付校验时对交付源码做关键词全局搜索抽查（localhost、固定IP、跨库jdbc等），抽查记录写入《软件测试报告》/交付核对清单。截图不作为唯一证据，以自查表+抽查记录为准；发现违规退回责任人整改。**
5. 全部交付物（源码、jar/dist、文档、UML源文件与图片、三套SQL、测试报告、演示视频）齐全并按目录打包。
