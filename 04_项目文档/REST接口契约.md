## 1. 全局约定

### 1.1 统一 JSON 返回格式

所有接口（含跨节点内部接口）必须返回以下统一结构：

```json
{
  "code": 200,          // 业务状态码
  "message": "操作成功", // 提示信息
  "data": {}            // 实际业务数据（无数据时为 {} 或 null）
}
```

**注意**：所有 HTTP 400/401/403/500 错误，响应体也必须遵循上述 JSON 结构。

错误返回示例：

```json
{ "code": 400, "message": "参数校验失败", "data": null }
```

### 1.2 全局 HTTP 状态码与业务错误码表

- `200`：成功

- `400`：仅用于请求参数缺失、类型错误、格式错误等参数问题（如时间格式错误、缺少必填项）；亦用于透传下游 3.5 返回的 400（message 保留下游原文）

- `401`：Token 缺失、格式非法、签名无效或过期，统一返回 401（前端需拦截并跳转登录）

- `403`：无权限（如普通学生调用管理员接口）（亦用于 4.2.8 订单不属于当前用户/不存在，不区分两者避免泄露存在性；前端拦截器须按 message/接口路径区分，不得一律跳登录页）

- `500`：服务器内部错误

**业务自定义错误码**（放在返回 JSON 的 `code` 字段中）：

- `1001`：座位已被预约（并发锁座失败；亦用于 3.3(3) 时段冲突）

- `1002`：预约参数不在可选范围内（档位不在 `duration_options` 内或超过 `max_duration_hours`、`startTime` 早于当前时刻、开始+时长超过预约开始日次日 00:00:00；见 4.2.1(1)(2)(3)）；亦用于 3.3(1) 座位侧时段越界

- `1003`：当前订单状态不允许此操作（如未到时间签到、4.2.3 取消超签到截止、3.3(4) 锁座幂等冲突、3.5 状态更新时占用记录不存在/已释放、4.2.6 主动离开时订单非已签到等；4.2.2/4.2.4/4.2.5③/4.2.6 透传座位 3.5 返回的 1003 亦属此码）

- `1004`：暂离已超时，业务已闭环（座位释放、订单转暂离超时释放、生成违约记录；HTTP 状态码 200，前端按提示处理，不做失败回滚。注：1004 仅用于暂离超时分支；到期分支返回 200 + status=已完成）

- `1005`：内部服务鉴权失败（内部服务 Token 校验失败，见 1.3；HTTP 状态码返回 401）

- `1006`：座位当前不可用（如处于维护、停用），不含时段冲突（时段冲突返回 1001）；亦用于：3.6.3 删除自习室、3.6.6 删除座位、3.6.7 调整座位状态时存在未释放占用记录（见 3.6.7）、3.2/3.3 中 `seatId` 不存在或已逻辑删除、3.2/3.3 中座位所属自习室已关闭（`room_info.status=0`）

- `1007`：外部依赖服务调用失败（如网络超时或拿不到下游响应报文，HTTP 状态码返回 200。注：下游正常业务错误仍透传原码，如 1001/1003/1006。另注：4.2.1 锁座网络失败返回 1007 且 HTTP 200；锁座成功但订单落库失败返回 HTTP 500，两者不混用）

- `1008`：该时段您已有其他预约（同一学生在时间重叠的时段已存在另一个非终态订单；见 4.2.1(4)）

- `2001`：账号或密码错误

- `2002`：账号已被禁用

- `2003`：账号（学号）已存在

> 说明：`2001-2003` 为身份权限子系统专属业务码，已由成员1提供并统一并入本表。

### 1.3 鉴权机制

- **用户端接口**：请求头必须携带 `Authorization: Bearer <JWT_Token>`。

- **内部服务接口（供定时任务/跨服务内部调用）**：请求头必须携带 `X-Internal-Token`，其值从各服务配置文件读取（配置项 `internal.token`），本文示例值 `campus_studyroom_internal_2026` 仅作联调参考，禁止硬编码在源码中；前端不得持有该 Token。

- **内部 Token 校验方式**：本项目为 4 个独立 SpringBoot 工程，不存在统一网关。凡契约标注为内部接口的路径，由**各服务自身拦截器**统一校验：请求头 `X-Internal-Token` 必须与配置值一致，否则拒绝；校验失败返回业务码 `1005`。8081 由成员1落地，8082 由成员2落地，8083 由成员3落地，8084 由成员4落地。

- **跨域**：所有 Controller 必须加 `@CrossOrigin`。

- **JWT 签名密钥（四服务共享）**：四个子系统统一使用同一签名密钥，配置项 jwt.secret，从外置配置读取。任一服务变更必须同步，否则统一返回 401。
  
  JWT Claims 约定：sub = userId（字符串形式的 Long）；userId = 同上；roles = 角色数组（如 ["STUDENT"]）；role = 主角色；exp = 过期时间。
  
  校验方式：8082/8083/8084 本地验签，不回调 8081；管理员接口判定 roles 数组是否包含 ADMIN。

### 1.4 跨节点服务地址配置规范（严禁硬编码）

开发时统一在 `application.yml` 中配置，代码使用 `@Value` 读取。联调参考 IP 如下：

- **节点A宿主机IP（身份/座位）**：`10.165.59.231`

- **节点B虚拟机IP（订单/通知）**：`192.168.56.101`

配置示例：

```yaml
remote:
  auth-service-url: http://10.165.59.231:8081
  seat-service-url: http://10.165.59.231:8082
  order-service-url: http://192.168.56.101:8083
  notify-service-url: http://192.168.56.101:8084

internal:
  token: campus_studyroom_internal_2026   # 联调参考值，各服务从外部配置读取，禁止硬编码
```

**ID 精度约定**：全局 `orderId` 若使用雪花算法生成 19 位 Long，后端返回前端时必须序列化为 String，防止前端 JS 精度丢失。

本文档中 `orderId` 示例为简化数字，实际按本节约定序列化为 String 返回前端；请求体中的 `orderId` 可接收数字或字符串，服务端统一按 Long 解析。

## 3. 座位资源子系统接口（成员2 负责实现）

### 3.1 获取自习室列表

- **路径**：`GET /api/rooms`

- **入参**：`pageNum`, `pageSize`

- **描述**：获取自习室列表。**学生调用仅返回 `status=1`（开放）的自习室**；**管理员调用返回全部（含 `status=0` 已关闭）**，以便重新开放。角色取自 JWT 的 `roles` 声明（见 1.3）。

- **出参**：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "total": 15,
    "pageNum": 1,
    "pageSize": 10,
    "list": [
      {
        "roomId": 1,
        "roomName": "第一自习室",
        "status": 1
      }
    ]
  }
}
```

- **字段说明**：`status`：`1`=开放，`0`=关闭。关闭的自习室其下座位不可被学生查询与预约（见 3.2、3.3）。

### 3.2 获取指定自习室的座位列表

- **路径**：`GET /api/rooms/{roomId}/seats`

- **入参**（Query）：

| 参数        | 类型     | 必填  | 说明                            |
| --------- | ------ | --- | ----------------------------- |
| startTime | string | 否   | 拟使用时段开始，`yyyy-MM-dd HH:mm:ss` |
| endTime   | string | 否   | 拟使用时段结束，`yyyy-MM-dd HH:mm:ss` |

> `startTime` / `endTime` **必须成对出现**：只传一个返回 HTTP 400；两个都不传时 `bookable` 返回 `null`，接口行为与 V3.3 完全一致（向后兼容）。

- **出参**：`status` 为**当前时刻粗状态**（枚举严格遵循需求：`可用`、`已预约`、`已占用`、`暂离中`、`维护`、`停用`）。语义：`已预约`=此刻被某订单占住但占的人还没签到；`已占用`=此刻有人签到在用；`暂离中`=在用但人暂离；`可用`=此刻没有任何订单占着（**即使未来被订住也不影响**）。`bookable` 为**所选时段的实际可约性**。两者语义不同，不得混用；**前端置灰只认 `bookable`，不得据 `status` 禁用座位**。

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "list": [
      { "seatId": 1, "seatNumber": "A-01", "status": "已占用", "bookable": true },
      { "seatId": 2, "seatNumber": "A-02", "status": "可用",   "bookable": false }
    ]
  }
}
```

- **业务规则**：
  
  （1）不传时段参数：`bookable` 返回 `null`，其余行为与 V3.3 完全一致（向后兼容）。
  
  （2）传时段参数时，`bookable=true` 当且仅当：座位状态非 `维护` / `停用`，**且**该时段 `[startTime, endTime)` 在该座位上**无未释放占用记录**。判据必须与 3.3(2) 完全一致，不得另立标准（否则会出现"列表显示可约、点进去返回 1001"）。
  
  （3）`status` 为 `维护` / `停用` 的座位，`bookable` **恒为 `false`**，不得因时段空闲返回 true。
  
  （4）`status` 仅供展示与筛选，**前端不得仅凭 `status` 置灰或禁用座位**（当前"已占用"的座位，其未来时段仍可预约；见需求 FR-STU-04 与 3.2 交互约束）。
  
  （5）时段格式错误返回 HTTP 400；`endTime <= startTime`、或 `endTime` 超过 `startTime` 所在自然日次日 `00:00:00`，返回业务错误码 `1002`。
  
  （6）`roomId` 不存在返回 `1006`；**学生调用且该自习室 `status=0`（已关闭）返回 `1006`**；管理员调用不受此限（便于维护已关闭自习室下的座位）。
  
  （7）本接口只读、不加锁；`bookable` 仅为**查询时刻的参考值**，并发下仍可能锁座返回 `1001`，最终以 3.3 结果为准。
  （8）`startTime` 早于当前系统时间时，`bookable` 恒为 `false`（此类时段在 4.2.1(2) 会被拒绝，本身不可下单），接口不为此返回错误码，便于前端统一按时段渲染；`startTime` 等于当前时间视为合法（与 4.2.1(2) 的 `>=` 一致）。

### 3.3 锁定座位（核心并发防重接口）

- **路径**：`POST /api/seats/{seatId}/lock`

- **请求头**：必须包含 `X-Internal-Token`。

- **描述**：供订单子系统（8083）在生成订单前调用。**订单子系统应用层必须预生成全局唯一 `orderId`**，该 `orderId` 仅作锁座与补偿关联标识，不要求订单已落库；锁座成功后才落库生成订单；锁座失败不落订单；落库失败必须补偿调用 3.4 释放。

- **入参**：

```json
{
  "orderId": 123456789,
  "startTime": "2026-10-25 14:00:00",
  "endTime": "2026-10-25 16:00:00", 
  "durationHours": 2
}
```

- **业务规则**：  
  （1）时间格式统一为 yyyy-MM-dd HH:mm:ss，格式错误返回 HTTP 400。校验 `endTime > startTime`；且 `endTime <= 预约开始日次日 00:00:00`（等于次日 00:00:00 时，视为到当天结束，合法、不算跨天）。**（注：由订单侧根据其配置的单位计算出实际的 endTime 后传入，座位侧不负责计算时长单位）**。durationHours 仅为日志与排障追溯而携带，不得参与任何时间计算、校验或落库；座位侧的实际时段一律以 endTime 为准，endTime 是唯一权威值。endTime <= startTime、或 endTime 超出上述边界时，返回 HTTP 200 + 业务错误码 1002（与订单侧 4.2.1(3) 同码，便于前端统一拦截；不得返回 400，400 仅用于格式与必填项问题）。
  （2）主判据为座位非维护/停用（若座位当前状态为“维护”或“停用”，直接返回 `1006`），且该时段无未释放占用记录；**当前粗状态不作为未来时段拒绝依据**。（注：内部实现必须配合 `SELECT ... FOR UPDATE` 锁定座位行，防并发超卖）。  
  （2-1）前置校验：`seatId` 不存在或已逻辑删除，返回 `1006`；座位所属自习室 `room_info.status=0`（已关闭），返回 `1006`。两项校验均须在加锁查询之前完成。
  
  （3）无冲突则插入占用记录，返回成功，座位状态按规则 (6) 处理（仅当所锁时段覆盖当前时刻且座位原为“可用”时置“已预约”，其余情况不动）；时段冲突返回错误码 1001。
  （4）幂等性要求：同一 `orderId` 重复锁座必须幂等。若存在未释放占用记录，返回原 `occupancyId`；若已释放或同 `orderId` 不同 `seatId`/时段，返回业务错误码 `1003`（当前订单状态不允许此操作），不得返回 200、不得新增占用；重新预约必须使用新 `orderId`。订单子系统在 4.2.1(6) 补偿释放后，该 `orderId` 在座位侧视为已终结；若再次使用该 orderId 发起锁座返回 1003 属预期。
  
  （5）座位侧不校验 `durationOptions` 和 `duration_unit_minutes`，仅根据传入的 `startTime` 和 `endTime` 校验时间边界与冲突；档位合法性由订单子系统 4.2.1 负责。
  
  （6）锁座成功后的座位状态：**仅当所锁时段覆盖当前时刻（`startTime ≤ 当前时间 < endTime`，因 (2) 已校验 `startTime ≥ 当前时间`，等价于"约的是立即开始的时段"）且该座位当前为 `可用` 时，置为 `已预约`**；其余情况（约的是未来时段、或座位当前为 `已占用`/`暂离中`/`维护`/`停用`）**一律不改动座位状态**。原因：`已预约` 只表达"此刻被订住、人还没签到"；若对"未来时段被订住"也写，会让"晚上有人约、下午空着"的座位在下午显示为已预约，误导他人。`已占用`/`暂离中` 只能由 3.5 写入。

- **响应示例**：

```json
{
  "code": 200,
  "message": "锁座成功",
  "data": {
    "occupancyId": 1001,
    "seatId": 1,
    "orderId": 123456789
  }
}
```

### 3.4 释放座位（供订单/通知子系统内部调用）

- **路径**：`POST /api/internal/seats/{seatId}/release`

- **请求头**：必须包含 `X-Internal-Token`。

- **入参**：

```json
{
  "orderId": 123456789,
  "action": "CANCEL" 
}
```

*(注：action 仅接收 CANCEL、TIMEOUT、FINISH，其他值返回 HTTP 400。)*

- **说明**：释放该 `orderId` 对应的占用记录（**只释放该订单对应的时段占用，不是整座置可用**）。释放后，座位粗状态**只按"当前时刻"重算，不问未来还有没有预约**。以下三条即《需求规格说明书》6.1 说明3 的同一规则，团队内简称"**三档回落**"：
  
  （1）若该座位处于 `维护` / `停用` → **保持原状态**（"维护"/"停用"），优先于其余各档；
  
  （2）若该座位仍存在**覆盖当前时刻**（`start_time ≤ 当前时间 < end_time`）的其他未释放占用记录 → **按该记录的 `checkin_flag` 分两种**，两种情况都在响应中回传 `coveringOrderId`（该覆盖记录的订单号，供调用方核对与排障）：
  
  - **`checkin_flag = 1`**（这单的人已经到过：已签到 / 暂离中 / 暂离后返回）→ **保持座位当前状态不变**（`已占用` 或 `暂离中`，由 3.5 早前写入）；本接口**不得**把它覆盖成 `已预约`。
  - **`checkin_flag = 0`**（这单的人还没到）→ 置 **`已预约`**（此刻被另一单占住，但占的人尚未签到）。
  
  > **为什么要在占用记录上记这个标记，而不是让订单侧回查补齐**：座位库与订单库分属两个节点，座位侧**禁止跨库查询**，调用方向也是订单→座位**单向下行**，座位侧不能反向问订单"这单的人到了没有"。而 3.5 的入参本就带 `orderId`——签到时座位侧当场就知道"是这单的人到了"，只要在那一刻把它记到占用记录上（`checkin_flag=1`），释放时自己就能判准。若不做这个标记，释放时只能一律置 `已预约`、再由调用方回查订单状态补调 3.5 改回 `已占用`：多一次跨服务调用，且每个调用 3.4 的分支（下单补偿、取消、到期、超时、暂离超时）都要重复写这段补齐逻辑，漏一处就会长期显示"人已到却为已预约"，且不报错、不告警。
  
  （3）若不存在覆盖当前时刻的未释放记录 → 状态回 **`可用`**，**无论未来是否还有开始时间晚于当前时刻的未释放记录**。
  
  > **`已预约` 的确切含义（V3.4 收紧）**：**此刻**这个座位被某个订单占住、而占的人还没签到。它**不表示"未来某时段被订住"**——A-01 上午 10:00 用完、晚上 19:00 另有人预约时，下午 14:00 该座位仍是 `可用`（此刻没有任何记录覆盖），`bookable` 也返回 true。V3.3 曾把它用于"未来有预约"，会导致整个下午显示已预约的误导，该用法废弃；**只在"覆盖当前时刻"时使用**。
  
  > **`seatStatus` 可能是 `已预约`**：释放后仍有覆盖此刻的其他记录、且**那单的人还没到**（`checkin_flag=0`）时返回 `已预约`；若**那单的人已到**（`checkin_flag=1`），则保持 `已占用`/`暂离中` 不变。两种情况下 `coveringOrderId` 都返回，仅供调用方核对，**调用方无需再补调 3.5**。
  
  **判定示例**（A-01：10:00 用完释放，19:00-21:00 有他人预约）：
  
  | 时刻             | `status` | 查 14:00-16:00 的 `bookable` | 查 19:00-21:00 的 `bookable` |
  | -------------- | -------- | -------------------------- | -------------------------- |
  | 11:00          | 可用       | true                       | false                      |
  | 19:00（到点、尚未签到） | **已预约**  | false（该时段已开始）              | false                      |
  | 19:30（已签到）     | 已占用      | false（早于当前时刻）              | false                      |
  | 22:00（用完释放）    | 可用       | —                          | false（早于当前时刻）              |
  
  释放前须校验 `orderId` 对应的未释放记录中 `seat_id` 与路径参数 `seatId` 一致，不一致返回 `1003`。
  
  > **释放即腾空，与返回的 `seatStatus` 无关**：本接口一旦把记录置 `release_status=1`，该 `[start_time, end_time)` 立即不再占用；紧随其后的空档（无其他未释放记录时）立即变为可预约——3.2 查询返回 `bookable=true`、3.3 锁座可通过。`seatStatus` 只是展示用快照，调用方**不得**据它推断“该座位接下来不能约”，也**不得**因它而跳过释放；典型场景：A 单 8:00-9:00 到期、B 单 9:00-10:00 同座位，9:00 释放 A 时——若 B 尚未签到（`checkin_flag=0`），`seatStatus` 为“**已预约**”；若 B 已经签到（`checkin_flag=1`），`seatStatus` **保持“已占用”**。两种情况 A 的时段都已腾空，10:00 之后的空档立即 `bookable=true`。
  
  > 判定口径须与《需求规格说明书》6.1 说明3、设计文档 3.2.2「释放状态更新规则」逐字一致，三处不得有差异。

- **幂等性要求**：  
  （1）同一 `orderId` 重复释放，若占用记录存在且 `release_status=1`，返回 HTTP 200 + `code=200`，`message="座位已释放"`，`data.occupancyId` 返回原占用记录 ID；  
  （2）若 `orderId` 在座位侧从未存在占用记录，返回 HTTP 200 + `code=200` 空操作，`message="无待释放占用记录"`，`data=null`；  
  （3）释放成功后，按上述“说明”中的逻辑重新计算并同步座位状态。

**响应示例**：

```json
{
  "code": 200,
  "message": "释放成功",
  "data": {
    "occupancyId": 1001,
    "seatId": 1,
    "seatStatus": "已预约",
    "coveringOrderId": 10002
  }
}
```

注：`seatStatus` 为释放后的实际判定结果，可能为 `可用`、**`已预约`**、**保持 `已占用`/`暂离中`**（覆盖此刻的那单人已到），也可能**维持 `维护`/`停用` 不变**；调用方不得硬断言为"可用"，也不得假定状态一定变化。`coveringOrderId` 仅作核对与排障参考，**不需要**据此补调 3.5。

### 3.5 更新座位状态（供订单子系统内部调用）

- **路径**：`POST /api/internal/seats/{seatId}/status`

- **请求头**：必须包含 `X-Internal-Token`。

- **描述**：供成员3（订单系统）在用户签到、暂离、暂离返回、以及**预约生效（到点未签到）**等场景下，通知座位子系统更新当前座位的物理粗状态。**该接口只做状态同步，不负责业务阈值判断**。

- **入参**：

```json
{
  "status": "已占用",
  "orderId": 123456789
}
```

*(注：`status` 字段仅接收 `已预约`、`已占用`、`暂离中` 三个值；不能通过此接口直接置为 `可用`、`维护`、`停用`，释放座位必须走 3.4 接口。其中 `已预约` 仅供 4.2.12 第 ④ 条"预约生效"使用，且**不会**置 `checkin_flag`)*

- **业务规则**：
  
  （1）校验本地必须存在 `orderId` 对应的未释放占用记录，且 `seatId` 一致；不满足或已释放返回 `1003`；传入的 `status` 不是"已预约""已占用""暂离中"三者之一，返回 HTTP 400。
  
  （2）校验通过后，**在同一次请求内**先更新 `seat_info.status` 为传入值，再按传入值决定是否置标记：
  
  - 传入 `已占用` 或 `暂离中` → 同时把该 `orderId` 的占用记录 `checkin_flag` 置 **1**（表示"这单的人已经到过"）；
  - 传入 `已预约` → **不置** `checkin_flag`（人还没到，只是座位的展示状态要跟着变）。
  
  （3）`checkin_flag` 置 1 后**不再回落**：暂离（写 `暂离中`）与暂离后返回（写 `已占用`）都保持 1。它回答的是"这个人来过没有"，不是"此刻在不在座"；后者由 `seat_info.status` 回答。
  
  > **为什么"已预约"必须单独处理**：`checkin_flag` 回答的是"这个人来过没有"。若 4.2.12 第 ④ 条"预约生效"调用本接口时也把它置 1，座位就会误判"人已到"，之后 3.4 释放第②档会保持"已占用"而不是置"已预约"，与需求 6.1 说明3 的结论相反。
  
  > **`checkin_flag` 只由本接口写、由 3.4 读**：3.4 释放时据此判断"覆盖此刻的那单的人到了没"，决定回落到 `已预约` 还是保持 `已占用`/`暂离中`。它是座位侧**唯一**能证明"该订单的人已到达"的本库依据——座位侧不能跨库查订单状态，也不能反向调用订单接口。

- **幂等性要求**：  
  （1）占用记录存在、`seatId` 一致且未释放：重复更新同一 `status` 返回 HTTP 200 + `code=200`；  
  （2）占用记录不存在或已释放：返回业务错误码 `1003`；  
  （3）`status` 不是"已预约""已占用""暂离中"三者之一：返回 HTTP 400。

- **路径**：`PUT /api/admin/seats/{seatId}/status`

- **入参**：

```json
{
  "status": "维护"
}
```

| 字段     | 类型     | 必填  | 说明                                                  |
| ------ | ------ | --- | --------------------------------------------------- |
| status | string | 是   | 仅接收 `可用`、`维护`、`停用`；传入 `已预约`/`已占用`/`暂离中` 返回 HTTP 400 |

- **业务规则**（唯一门槛：**该座位已经没有任何未释放的时段占用记录**）：
  
  （1）若存在**覆盖当前时刻**的未释放记录（座位正在使用或暂离中）→ 拒绝，返回业务错误码 `1006`，`message="座位正在使用中，无法设置维护/停用"`，`data.affectedOrders` 为空数组。
  
  （2）若不存在覆盖当前时刻的记录、但仍有**未来**未释放记录 → 拒绝，返回业务错误码 `1006`，并在 `data.affectedOrders` 中返回这些记录（`orderId` + 时段），提示"请先取消受影响的预约"。
  
  （3）该座位已无任何未释放记录 → 更新座位状态为成功，`data.affectedOrders` 为空数组（字段保留以固定响应结构）：

```json
{
  "code": 200,
  "message": "状态更新成功",
  "data": {
    "affectedOrders": []
  }
}
```

> **只返回 `orderId` 与时段，不返回 `userId`**：座位库的 `seat_occupancy` 只有 `seat_id`/`order_id`，没有 `user_id`（用户归属在订单库），座位侧也无权跨库查询。前端拿到 `orderId` 后调用 4.2.3（管理员分支），由订单侧按 `orderId` 查出归属用户并推送取消通知。

  （4）**责任边界**：座位侧只负责改状态并返回受影响清单，**不取消订单、不调用订单子系统**（调用链为订单→座位的单向下行）。

  （5）**顺序不得颠倒**：前端须按 ① 提交（被拒绝，取清单）→ ② 对清单逐个调 4.2.3（管理员分支）取消 → ③ 全部成功后**再提交一次**的顺序执行。反了会留下"座位已维护 + 订单仍待签到"的无效状态——学生次日要么签不了到被误记违约，要么签到成功把"维护"覆盖成"已占用"。

  （6）除上述外，其余规则同 V3.3：`status` 取值校验、座位不存在/已删除校验等不变。

- **出参中的 `data`**：`affectedOrders` 数组（元素为 `orderId`、`startTime`、`endTime`）；设置成功、或"座位正在使用中"时为空数组。【前端取值约定】弹窗清单取自**第 ① 步（被拒绝那次）的响应**，不是取自设置成功之后。
  
  > **为什么没有"强制"开关**：V3.3 曾设计 `force=true` 表示"有未来预约也能强行设维护"。该做法会留下"座位=维护、订单=待签到"的死数据（学生次日要么签不了到被误记违约，要么签到成功把"维护"覆盖成"已占用"），且与"先取消后维护"的规则自相矛盾。V3.4 起**取消该参数**：想设维护，就必须先把受影响的预约退掉；"强制"由前端"批量取消 + 再次提交"完成，服务端不提供任何绕过入口。

### 4.2 订单流转子系统（8083）- 负责人：成员3

**调用座位子系统接口通用说明**

本子系统调用座位资源子系统 `lock / release / status` 接口均携带内部鉴权头 `X-Internal-Token`；lock 请求体为 `{orderId, startTime, endTime, durationHours}`，release 请求体为 `{orderId, action}`，status 请求体为 `{status, orderId}`；座位合法业务错误进行透传，网络无响应返回 1007。

**跨节点调用超时与重试约定**：各子系统间 HTTP 调用必须显式设置超时，禁止使用框架默认值。约定 **connect 2000ms、read 5000ms**（配置项 `remote.connect-timeout-ms` / `remote.read-timeout-ms`，从外置配置读取）。超时抛出即视为“网络层面无法获取下游响应”，按 1007 处理；**写操作（锁座、释放、状态同步、消息推送）一律不自动重试**，避免重复执行导致状态错乱，由用户重试或人工按日志处理；只有幂等读取类接口（4.2.11 配置读取）允许最多重试 1 次。

**本地落库失败兜底**：4.2.2～4.2.6 中，若座位接口成功、但订单本地更新失败，接口返回 HTTP 500。订单子系统记录补偿日志，**本契约不承诺自动重试**。一致性由 **用户重复提交（各接口幂等）** 或 **人工按日志处理** 收敛。已知副作用：用户不重试则可能被 4.2.12 判为超时释放并记违约，前端收到 500 应提示“操作未完成，请重试”。

**状态流转日志（强制）**：以下状态变更必须在同一本地事务内写入 `order_status_log`（含 from、to、operator_type；`operator_type` 取值 `STUDENT` 学生本人操作 / `ADMIN` 管理员操作 / `SYSTEM` 定时任务）：4.2.1创建、4.2.2签到、4.2.3取消、4.2.5①、4.2.5②、4.2.6主动离开、4.2.12①②③。4.2.4暂离记 `from_status=to_status=已签到`。

#### 4.2.1 创建预约下单

- **路径**：`POST /api/orders/reserve`
- **描述**：学生发起座位预约；服务端预生成orderId，锁座请求携带该orderId；锁座成功才生成【待签到】订单，锁座失败不生成订单。锁座成功若本地订单落库失败，使用同一orderId执行座位release，action=CANCEL做补偿释放。
- **鉴权说明**：用户接口，请求头携带 `Authorization: Bearer <JWT_Token>`
- **入参**：

```json
{
  "seatId": 1,
  "startTime": "2026-10-25 14:00:00",
  "durationHours": 2
}
```

- **业务规则**：

(1) 校验 `durationHours` 属于本地 `BIZ_CONFIG.duration_options` 且 `durationHours ≤ max_duration_hours`；`durationHours` 表示**时长档位数**，实际时长 = `durationHours × duration_unit_minutes`（`BIZ_CONFIG.duration_unit_minutes`，生产 `60`，测试 `1`）。档位非法（不在 `duration_options` 内或超过 `max_duration_hours`）返回业务错误码 `1002`。

(2) 校验 `startTime` >= 当前系统时间，不满足返回业务错误码 `1002`（`startTime` 等于当前时刻视为合法）；

(3) 校验 startTime + durationHours × duration_unit_minutes <= 预约开始日次日 00:00:00，不满足返回业务错误码 1002；

(4) 校验同一学生时段不重叠：若该 `userId` 已存在状态为【待签到】或【已签到】的订单，且与本单时段满足 `已有订单.startTime < 本单.endTime AND 已有订单.endTime > 本单.startTime`，则返回业务错误码 `1008`，不锁座、不落库。相邻时段不算重叠（前单 `endTime` = 本单 `startTime` 时允许）；已终态订单（已完成/已取消/超时释放/暂离超时释放）不参与校验；不同日期的同一时段不受限制。**本条必须先于 (5) 锁座执行**，否则会出现"先锁座、校验失败再补偿释放"的多余调用。

(5) 远程调用座位子系统锁座接口 `POST /api/seats/{seatId}/lock`；锁座返回 `1001/1003/1006` 错误时直接透传错误，不生成订单；网络层面无法获取座位子系统响应则返回业务错误码=1007（HTTP状态码200），不生成订单。

(6) 锁座成功，尝试生成订单；若订单落库失败，调用座位释放接口 `POST /api/internal/seats/{seatId}/release`，action 传值 `CANCEL` 做补偿；若补偿释放也失败，记录补偿失败日志（含 `orderId`、`seatId`、失败原因、时间），由运维/开发按日志人工重试释放；本契约不承诺自动重试。最终向用户返回 HTTP 500，响应体必须遵循 1.1 统一 JSON 格式，即 {"code": 500, "message": "服务器内部错误", "data": null}，不得返回原生异常堆栈。

(7) 落库成功生成订单，订单状态为待签到；异步调用通知子系统消息推送接口 `POST /api/internal/notify/push`，`eventType` 传 `RESERVE_SUCCESS`，`dedupKey` 传 `RESERVE_SUCCESS:{orderId}` 推送预约成功消息，推送失败仅记录日志，不阻塞订单主流程。

- **响应示例**：

```json
{
  "code": 200,
  "message": "预约下单成功",
  "data": {
    "orderId": 10001,
    "seatId": 1,
    "status": "待签到",
    "startTime": "2026-10-25 14:00:00",
    "endTime": "2026-10-25 16:00:00"
  }
}
```

#### 4.2.2 订单签到

- **路径**：`POST /api/orders/{orderId}/sign-in`

- **描述**：学生执行订单签到；校验签到守卫条件；**先调用座位子系统状态更新接口，调用成功后再更新本地订单状态**；座位接口调用失败（网络超时/下游无响应）则订单状态保持原样，返回业务错误码=1007（HTTP状态码200），本地状态不变，用户可重试（接口幂等）。

- **鉴权说明**：用户接口，请求头携带 `Authorization: Bearer <JWT_Token>`

- **入参**：路径变量 `orderId`，无请求体

- **业务规则**：  
  (1)校验该订单属于当前登录用户；  
  (2)校验订单状态必须为【待签到】，否则返回业务错误码 `1003`；  
  (3)签到守卫条件：`预约开始时间 ≤ 当前时间 ≤ 预约开始时间 + 签到截止时长`；不满足条件返回业务错误码 `1003`；  
  (4)先远程调用座位子系统接口 `POST /api/internal/seats/{seatId}/status`，设置座位状态为“已占用”；座位子系统返回业务错误则直接透传code与message，不修改订单状态；  
  (5)座位接口调用成功，才更新本地订单状态为已签到；座位接口网络层面调用失败、无法获取响应，订单状态不变，返回业务错误码=1007（HTTP状态码200），本地状态不变，用户可重试（接口幂等）。

- **响应示例**：

```json
{
  "code": 200,
  "message": "签到成功",
  "data": {
    "orderId": 10001,
    "status": "已签到",
    "seatStatus": "已占用"
  }
}
```

#### 4.2.5 暂离返回（重新签到）

- **路径**：`POST /api/orders/{orderId}/return-back`

- **描述**：学生暂离之后返回，执行重新签到；做三段业务校验：使用到期优先、暂离超时、正常返回；**优先调用座位子系统接口，接口成功后再变更订单状态、清空暂离时间；超时分支异步推送消息**。

- **鉴权说明**：用户接口，请求头携带 `Authorization: Bearer <JWT_Token>`

- **入参**：路径变量 `orderId`，无请求体

- **业务规则**：  
  (1)校验该订单属于当前登录用户；  
  (2)校验订单状态必须为【已签到】且处于暂离中（`tempLeaveStartTime`不为空），否则返回业务错误码 `1003`；
  
  (3)三段校验逻辑：
  
  ① 如果当前时间 ≥ 预约结束时间：  
  先调用座位子系统release接口，action传值`FINISH`；座位子系统返回业务错误则直接透传code与message，本地不做变更；座位调用成功；订单转为已完成；清空`tempLeaveStartTime`；不生成违约记录；不推送消息**（此处不推送：该终态由学生本人当次请求直接触发并同步返回结果，无需再推；定时路径 4.2.12① 属无人值守触发，故必须推送 USE_EXPIRED_COMPLETE。两条路径终态一致，仅推送策略不同。）；网络调用失败，本地不变更，返回业务错误码=1007（HTTP状态码200），本地状态不变，用户可重试（接口幂等）*。
  
  ② 如果当前时间 > 暂离开始时间+暂离保留上限 且 当前时间＜预约结束时间：  
  先调用座位release接口，action传值`TIMEOUT`；座位子系统返回业务错误则直接透传code与message，本地不做变更；座位调用成功；订单转为暂离超时释放；生成违约记录（类型`暂离超时`）；清空`tempLeaveStartTime`；异步调用通知子系统接口 `POST /api/internal/notify/push`，`eventType` 传 `TEMP_LEAVE_TIMEOUT_RELEASE`，`dedupKey` 传 `TEMP_LEAVE_TIMEOUT_RELEASE:{orderId}`；推送失败仅记日志不阻塞；返回业务错误码`1004`；网络调用失败，本地不变更，返回业务错误码=1007（HTTP状态码200），本地状态不变，用户可重试（接口幂等）。“HTTP 状态码 200，前端按提示处理，不做失败回滚”，与 1.2 呼应。
  
  ③ 其余情况为正常返回：  
  先调用座位status接口设置为“已占用”；座位子系统返回业务错误则直接透传code与message，本地不做变更；座位调用成功；清空`tempLeaveStartTime`；订单保持已签到；网络调用失败，本地不变更，返回业务错误码=1007（HTTP状态码200），本地状态不变，用户可重试（接口幂等）。

```json
  "message": "返回座位成功",
  "data": {
    "orderId": 10001,
    "status": "已签到",
    "seatStatus": "已占用",
    "tempLeaveStartTime": null
  }
}
```

#### 4.2.12 内部‑批量触发订单超时处理

- **路径**：`POST /api/internal/orders/batch-handle-timeout`

- **描述**：仅供监控通知子系统（8084）定时任务调用；扫描订单，执行到期、超时未签到、暂离超时处理；**禁止前端调用。业务阈值读取订单子系统本地BIZ_CONFIG配置，调用方不传入判断阈值。**

- **鉴权说明**：内部接口，请求头必须携带 `X-Internal-Token`，取值与服务配置项 `internal.token` 保持一致；联调参考示例值见 1.3，禁止在业务代码硬编码 token。前端禁止访问。鉴权失败返回业务错误码 `1005`。

- **入参**：无请求体

- **业务规则**：

(1)读取本地业务配置（签到截止时长、暂离保留上限）；

(2)只处理非终态订单；已为终态订单直接跳过，保证幂等；订单状态更新使用条件更新（where status=非终态）；订单状态变更与违约记录生成放在本地事务；重复扫描不会重复生成违约、不会重复触发消息；座位释放失败跳过本轮，记录日志，此时订单状态保持非终态不变，等待下一轮重试。

(3)扫描分支严格按使用到期优先：

- ① 使用到期：订单状态=已签到（含暂离中）且 `当前时间 >= endTime`；先调用座位释放接口 `action=FINISH`；座位调用成功，订单置`已完成`，清空`tempLeaveStartTime`，不生成违约记录；异步调用通知子系统接口 `POST /api/internal/notify/push`，`eventType` 传 `USE_EXPIRED_COMPLETE`，`dedupKey` 传 `USE_EXPIRED_COMPLETE:{orderId}`，推送使用到期提示消息，推送失败仅记日志。座位释放失败记录日志，计入`seatReleaseFailed`，该订单跳过本次处理；

- ② 超时未签到：订单状态=待签到 且 `当前时间 > startTime + 签到截止时长`；先调用座位释放接口 `action=TIMEOUT`；座位调用成功；订单置`超时释放`；生成违约记录（类型`超时未签到`）；异步调用通知子系统接口 `POST /api/internal/notify/push`，`eventType` 传 `SIGN_IN_TIMEOUT_RELEASE`，`dedupKey` 传 `SIGN_IN_TIMEOUT_RELEASE:{orderId}`；推送失败仅记日志；座位释放失败记录日志，计入`seatReleaseFailed`，订单跳过本次处理；

- ③ 暂离超时：订单状态=已签到，`tempLeaveStartTime`不为空，`当前时间 > tempLeaveStartTime + 暂离保留上限` 且 `当前时间 < endTime`；先调用座位释放接口`action=TIMEOUT`；座位调用成功；订单置`暂离超时释放`；生成违约记录（类型`暂离超时`）；异步调用通知子系统接口 `POST /api/internal/notify/push`，`eventType` 传 `TEMP_LEAVE_TIMEOUT_RELEASE`，`dedupKey` 传 `TEMP_LEAVE_TIMEOUT_RELEASE:{orderId}`；推送失败仅记日志；座位释放失败记录日志，计入`seatReleaseFailed`，订单跳过本次处理。

- ④ **预约生效**（只同步座位展示状态，**不改变订单状态、不生成违约、不计入任何统计**）：订单状态=待签到 且 `startTime <= 当前时间 <= startTime + 签到截止时长`（已进入时段、尚未超时，与 ② 互斥）；若该订单对应座位当前为 `可用`，调用 3.5 置 `已预约`。目的：让"到点了但人还没来"的座位显示为"已预约"而不是"可用"。

> 说明：本接口虽名为"超时处理"，实际是订单侧**唯一的一轮定时扫描入口**，"预约生效"与三类超时处理在同一轮内完成，不新增任务。座位状态**最多滞后一个扫描周期**；可约性判定始终以占用记录为准，不受此滞后影响。

（4）座位释放失败不阻塞整体扫描流程，记录日志统计失败数；消息推送失败仅记录日志，不阻塞扫描主流程。`messagePushTriggered` 统计触发推送调用次数（无论推送成功或失败）。
（5）统计输出：总处理数、签到超时释放数、暂离超时释放数、到期完成数、生成违约记录数、座位释放失败数、触发消息推送数。**订单子系统不落库**（订单侧无对应表）；统计字段为本次调用的运行时简报。**通知子系统可将本次调度结果写入本地 `notify_task_log`**（执行时间 `execute_time`、各计数、执行耗时 `cost_ms`、触发方式 `trigger_type`），字段与 `init_nodeB.sql` 中该表逐列对应，该表仅用于留档与排障，**不参与任何业务判断**，也不作为对账依据；本接口响应不依赖该表。

**响应示例**：

```json
{
  "code": 200,
  "message": "批量超时扫描执行完成",
  "data": {
    "handleCount": 2,
    "signInTimeoutReleased": 1,
    "tempLeaveTimeoutReleased": 0,
    "expiredCompleted": 1,
    "violationCreated": 1,
    "seatReleaseFailed": 0,
    "messagePushTriggered": 1 
  }
}
```

注：“响应字段为驼峰，与数据库下划线字段一一对应”

#### 4.3.4 内部消息推送（供订单等子系统调用）

- **路径**：`POST /api/internal/notify/push`

- **鉴权**：内部接口，请求头必须携带 `X-Internal-Token`，取值与服务配置项 `internal.token` 保持一致；联调参考示例值见 1.3，禁止在业务代码硬编码 token。前端禁止访问。鉴权失败返回业务错误码 `1005`。

- **描述**：订单子系统在预约成功、超时释放、暂离超时释放、到期完成等事件后调用；通知子系统只入库并推送，不反查订单、不调座位接口。

- **入参**：

```json
{
  "eventType": "SIGN_IN_TIMEOUT_RELEASE",
  "userId": 1002,
  "orderId": 10001,
  "title": "预约超时释放",
  "content": "您预约的座位因超时未签到已释放",
  "bizTime": "2026-10-25 14:20:00",
  "dedupKey": "SIGN_IN_TIMEOUT_RELEASE:10001"
}
```

| 字段        | 必填  | 说明                                           |
| --------- | --- | -------------------------------------------- |
| eventType | 是   | 事件类型，见下方枚举                                   |
| userId    | 是   | 接收用户 ID                                      |
| orderId   | 否   | 关联订单 ID；系统消息可为空                              |
| title     | 是   | 消息标题，≤100 字符                                 |
| content   | 是   | 消息内容，≤500 字符                                 |
| bizTime   | 是   | 业务发生时间，格式 `yyyy-MM-dd HH:mm:ss`              |
| dedupKey  | 是   | 幂等键，建议 `eventType:orderId`；重复调用返回原 messageId |

- **事件类型枚举（已冻结）**：

| 枚举                           | 触发场景                                   |
|:---------------------------- |:-------------------------------------- |
| `RESERVE_SUCCESS`            | 预约成功（订单 4.2.1）                         |
| `SIGN_IN_TIMEOUT_RELEASE`    | 超时未签到释放（订单 4.2.12②）                    |
| `TEMP_LEAVE_TIMEOUT_RELEASE` | 暂离超时释放（订单 4.2.5②、4.2.12③）              |
| `USE_EXPIRED_COMPLETE`       | 使用到期完成（订单 4.2.12①，必推，推送失败仅记录日志，不阻塞主流程） |
| `SYSTEM`                     | 系统消息（预留；管理员因座位维护取消预约时使用，见 4.2.3）       |

**订单侧调用报文模板（订单→通知）**：

| eventType                    | userId    | orderId | title  | content         | bizTime | dedupKey                               |
| ---------------------------- | --------- | ------- | ------ | --------------- | ------- | -------------------------------------- |
| `RESERVE_SUCCESS`            | 订单.userId | orderId | 预约成功   | 您已成功预约座位，请按时签到  | 下单时间    | `RESERVE_SUCCESS:{orderId}`            |
| `SIGN_IN_TIMEOUT_RELEASE`    | 订单.userId | orderId | 预约超时释放 | 您预约的座位因超时未签到已释放 | 释放时间    | `SIGN_IN_TIMEOUT_RELEASE:{orderId}`    |
| `TEMP_LEAVE_TIMEOUT_RELEASE` | 订单.userId | orderId | 暂离超时释放 | 您暂离超过规定时限，座位已释放 | 释放时间    | `TEMP_LEAVE_TIMEOUT_RELEASE:{orderId}` |
| `USE_EXPIRED_COMPLETE`       | 订单.userId | orderId | 使用到期完成 | 您的预约已到期，座位已释放   | 到期时间    | `USE_EXPIRED_COMPLETE:{orderId}`       |
| `SYSTEM`                     | 订单.userId | orderId | 预约已取消  | 因座位维护，您的预约已被取消  | 取消时间    | `SYSTEM:{orderId}`                     |

**业务规则**：

1. `dedupKey` 唯一，重复推送返回原 `messageId` 且 `duplicated=true`，不重复入库。

2. 推送失败只记录 `notify_push_log`，不向调用方抛异常；调用方按“推送失败不阻塞主流程”处理。推送失败时仍返回 HTTP 200 + `code=200`，`message="消息已入库，推送失败已记录"`，`data` 含 `messageId`、`duplicated=false`、`pushStatus="FAIL"`；调用方只记日志，不重试、不回滚。pushStatus 记录仅作留档与排障追溯，不参与任何自动重推；本契约不设“失败消息重推”任务，恢复后仅保证新事件推送恢复正常。

3. 参数缺失/格式错误返回 HTTP 400；内部 Token 错误返回业务码 `1005`。
- **响应示例**：

```json
{
  "code": 200,
  "message": "推送成功",
  "data": {
    "messageId": 1001,
    "duplicated": false,
    "pushStatus": "SUCCESS"
  }
}
```

```json
  "message": "消息已存在",
  "data": {
    "messageId": 1001,
    "duplicated": true,
    "pushStatus": "SUCCESS"
  }
}
```

- **描述**：手动触发一次与定时任务相同的补偿扫描，内部调用订单 `POST /api/internal/orders/batch-handle-timeout`（4.2.12）。用于成员6容错测试恢复后立即验证，不必等定时周期；定时任务本身自动执行，不依赖本接口。

- **入参**：无

- **业务规则**：本接口不处理订单、不释放座位，只透传订单 4.2.12 的处理统计；订单返回业务错误码时透传。

- **响应示例**：

```json
{
  "code": 200,
  "message": "补偿扫描触发完成",
  "data": {
    "handleCount": 2,
    "signInTimeoutReleased": 1,
    "tempLeaveTimeoutReleased": 0,
    "expiredCompleted": 1,
    "violationCreated": 1,
    "seatReleaseFailed": 0,
    "messagePushTriggered": 1
  }
}
```

#### 4.3.6 定时任务说明（非接口）

- 通知子系统定时任务按本服务配置的扫描周期执行，调用订单 `POST /api/internal/orders/batch-handle-timeout`（4.2.12）触发处理；

- 不自行计算业务阈值，不调用座位 3.4/3.5；

- 订单 4.2.12 内部异步调用 4.3.4 完成消息推送；推送失败仅记通知侧日志，不影响订单主流程；

- **通知子系统不做任何业务阈值判断**（签到截止、暂离上限、到期判定全部在订单侧 4.2.12 内部完成）：调度周期只取本服务配置 `notify.scan.interval`，**不读取 `scanIntervalSeconds`、不把任何配置值用于判断**；`biz_config.scan_interval_seconds` 仅为留档，订单侧也不读它。4.2.11 保留供联调核对与排障，定时任务不依赖其返回值。

## 5. 内部接口调用链路清单（基线定调）

为了保证分布式架构下各子系统的边界清晰，严格遵循“禁止跨库直连”与“谁调用谁主导联调”的原则，内部跨节点调用链路基线如下：

（1）**订单流转子系统 (8083) 调用 座位资源子系统 (8082)**

- **锁座**：`POST /api/seats/{seatId}/lock` (订单应用层预生成 orderId 传入，锁座成功后才落订单)
- **释放座位**：`POST /api/internal/seats/{seatId}/release` (幂等)
- **状态同步**：`POST /api/internal/seats/{seatId}/status` (仅接收“已占用/暂离中”，幂等)
- *(注：上述接口均由成员2定义，成员3负责发起调用)*

（2）**订单流转子系统 (8083) 调用 监控通知子系统 (8084)**

- **消息推送**：订单状态变更时，异步调用通知子系统接口。推送失败不可阻塞订单主流程。
- *(注：具体接口契约由成员4定义，成员3负责发起调用)*

（3）**监控通知子系统 (8084) 调用 订单流转子系统 (8083)**

- **配置读取**：`GET /api/internal/config/business`（4.2.11，**可选、仅供排障核对**；定时任务不依赖其返回，业务阈值一律在订单侧 4.2.12 内部判断，严禁通知侧自行建表存储配置）
- **批量扫描触发**：`POST /api/internal/orders/batch-handle-timeout` (触发超时/到期处理)
- *(注：具体接口契约由成员3定义，成员4负责发起调用)*

（4）**前端直接调用 8082 接口**

- **管理员维护**：管理员的自习室/座位 CRUD、座位状态调整，由 Web 前端直接调用座位资源子系统（8082）的 `3.6` 接口，不经过订单/通知子系统。
